- 根因1：API 返回 `content: null` 时代码没有防御处理
- 根因2：`max_tokens=2048` 可能导致长 JSON 输出被截断（`finish_reason: length`）
- 根因3：LLM 返回的 JSON 可能包含注释、控制字符、或被截断导致格式不完整

    - 增加 `finish_reason` 日志，当 `finish_reason=length` 时输出警告
    - 返回值新增 `finish_reason` 字段供上层使用
    - 同步修复 `_call_zhipu_api()` 和 `_call_ollama_api()` 的同类问题

57. **增大 `_process_sql_with_custom_prompt()` 的 max_tokens** (`requirement_analyzer.py`)
    - 从默认 2048 改为 `max_tokens=4096`，减少 JSON 输出被截断的概率
    - 增加 `finish_reason` 检查，截断时记录警告到 process_log
    - LLM 返回空内容时自动重试一次
    - 增加详细诊断日志：`repr(raw_output[:100])`、finish_reason
    - `content` 取值从 `.get('content', '')` 改为 `.get('content') or ''`，防御 None

    - 保留原有3种策略 + 新增4种容错策略（共7步）：
      1. 直接解析（纯JSON）
      2. 提取 ```json 代码块
      3. 提取第一个 `[` 到最后一个 `]` 之间的内容
      4. 【新增】以上每步增加 `_clean_json_text()` 清理后重试
      5. 【新增】截断修复：找最后一个 `}` 补上 `]`
      6. 【新增】逐对象提取：遍历花括号配对，逐个 `json.loads({...})`
    - 新增 `_clean_json_text()` 辅助函数：
      - 移除行注释 `// ...`
      - 移除值后行尾注释 `, // ...`
      - 移除不可见控制字符（保留换行/回车/Tab）
    - 每步失败时记录具体的 JSONDecodeError 信息（不只是"解析失败"）
    - 全部失败时记录原始文本前300字符 + 后100字符（用 repr 显示不可见字符）

## Phase D：意图分类（Intent Classification）系统引入

### 背景
- 用户提供了一个专业的 Prompt 模板，引入 **意图分类**（`SQL_TEST` / `DOC_PROOF` / `UI_PROOF`）
- LLM 返回格式从旧的 JSON 数组 `[{test_case}]` 变更为 JSON 对象 `{intent, extracted_points, test_cases}`
- 只有 `SQL_TEST` 意图才触发实际 SQL 执行；`DOC_PROOF`/`UI_PROOF` 返回证明方式建议

### 修改内容

59. **重写 `_parse_llm_json_response()`**（从 `_parse_llm_json_test_cases` 重命名）
    - 支持新格式 `{intent, extracted_points, test_cases}` 和旧格式 `[{test_case}]`
    - 内部 `_normalize_result()` 统一转换为新格式
    - 5+种解析策略：直接解析 → 代码块提取 → 花括号提取（对象）→ 方括号提取（数组）→ 截断修复（对象/数组/逐对象）
    - 每步增加 `_clean_json_text()` 清理后重试

60. **重构 `_process_sql_with_custom_prompt()` 增加意图分支**
    - 解析 LLM 返回后根据 `intent` 字段分支：
      - `SQL_TEST` + `test_cases` → 调用 `_handle_sql_test_intent()`
      - `DOC_PROOF`/`UI_PROOF` → 调用 `_handle_non_sql_intent()`
      - 其他情况：有 test_cases 仍执行；无 test_cases 返回考点列表

61. **新增 `_handle_sql_test_intent()`** (`requirement_analyzer.py`)
    - 从 `_process_sql_with_custom_prompt` 中提取的 SQL 测试执行逻辑
    - 运行 `_execute_test_cases()`，构建 process_log 的 tool_calls，生成 markdown 表格答案
    - 返回 `{intent='SQL_TEST', extracted_points, confidence=0.8}`

62. **新增 `_handle_non_sql_intent()`** (`requirement_analyzer.py`)
    - 处理 DOC_PROOF/UI_PROOF 意图
    - 生成描述性答案：意图标签 + 说明 + 考点列表 + 证明方式建议
    - 返回 `{confidence=0.7, sql_results=None, test_cases=None}`

63. **`_classify_and_process_unmatched()` 传播 intent/extracted_points**
    - combined / sql_validation 返回值中新增 `intent` 和 `extracted_points` 字段
    - 从 `sql_result_data` 中提取并合并到最终结果

64. **前端 `displayBatchAnalysisResults()` 新增意图展示** (`chat_doc.html`)
    - 意图徽章：绿色=SQL_TEST、蓝色=DOC_PROOF、橙色=UI_PROOF
    - extracted_points 标签云：在需求内容和答案之间展示提取的考点

65. **`export_to_word()` 支持 intent/extracted_points** (`requirement_analyzer.py`)
    - 匹配类型标签后新增【意图分类】段落（带颜色：绿/蓝/橙）
    - 新增【提取的考点】编号列表（缩进1cm）
    - DOC_PROOF/UI_PROOF：显示【证明方式建议】（文档来源 / 截图方式），不展示 SQL
    - SQL_TEST 或无 intent：保留原有 test_cases 逐条 SQL 执行展示

### 用户 Prompt 模板使用说明
- 通过前端 Prompt 配置弹窗（⚙️ Prompt → SQL提取验证 Tab）粘贴模板并保存
- 模板末尾 `{待解析的具体技术要求}` 需替换为 `{{requirement}}`（系统变量占位符）
- `render_prompt()` 使用 `re.sub(r'\{\{(\w+)\}\}', ...)` 进行变量替换
- 渲染时传入 `{'requirement': content, 'db_types': db_types_desc}`
